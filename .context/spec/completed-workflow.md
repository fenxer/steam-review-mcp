# Completed Workflow

## When to Use This Workflow

- Spec status is "Completed"
- All implementation tasks have been finished
- Final validation and documentation is needed
- Specification is ready for archival

## Workflow Steps

### Phase 1: Final Validation
- Verify all success criteria are met
- Confirm all tasks in Implementation Status are marked complete
- Validate that implementation matches original requirements
- Document any final deviations or lessons learned

### Phase 2: Documentation & Archival
- Complete final entries in Completed Work section
- Ensure Change Log captures all modifications made during execution
- Add final summary and outcomes
- Mark specification as archived

### Phase 3: Knowledge Transfer
- Share lessons learned with team
- Update project documentation if needed
- Archive specification for future reference
- Extract reusable patterns or practices

## Final Documentation Requirements

### Completed Work (Final)
**Purpose**: Complete record of all implementation activities

**Final Requirements**:
- All completed tasks with links to actual changes
- Summary of major milestones and decisions
- Final metrics (time spent, lines of code, etc.)
- Any deviations from original plan with explanations

### Change Log (Final)
**Purpose**: Complete audit trail of all plan modifications

**Final Requirements**:
- All modifications made during execution phase
- Impact analysis for each change
- Authorization records for all adjustments
- Summary of how changes affected final outcome

### Final Summary (Optional)
**Purpose**: High-level overview of the completed work

**Content**:
- Implementation success against original requirements
- Key challenges and how they were resolved
- Lessons learned for future similar work
- Recommendations for improvements

## Archival Process

### File Management
1. Ensure specification file is complete and self-contained
2. Verify all cross-references and links are valid
3. Add final timestamp to "Last Updated" field
4. Move to appropriate archive location if needed

### Knowledge Extraction
1. Identify reusable patterns or components created
2. Document any new best practices discovered
3. Update team knowledge base or documentation
4. Share insights with relevant stakeholders

## ⚠️ CRITICAL: Post-Completion Modifications

### Absolute Immutability Principle
Once marked as "Completed", the specification becomes **STRICTLY READ-ONLY** for historical purposes.

**ZERO TOLERANCE**: No direct modifications allowed under any circumstances.

### MANDATORY Modification Process
If changes are needed to completed work:

⚠️ **STRICT REQUIREMENTS**:
- **MUST** use ADDENDUM system (no exceptions)
- **MUST** reference original specification exactly
- **MUST** create new specification file following ADDENDUM naming convention
- **MUST** follow complete specification process for new work

**VIOLATION CONSEQUENCES**: Any direct modifications to completed specifications will be immediately rejected and flagged for correction.

### Required ADDENDUM Process
1. **MANDATORY**: Follow "ADDENDUM System" section in @.context/spec/modification-rules.md
2. **MANDATORY**: Use exact file naming: `ADDENDUM-{original-spec-id}-{sequence}-{description}.md`
3. **MANDATORY**: Include proper references to original completed work
4. **MANDATORY**: Follow complete specification workflow for new additions

**📖 STRICT COMPLIANCE REQUIRED**: @.context/spec/modification-rules.md

### Enforcement
- All completed specifications are protected from modification
- Any violation will trigger immediate correction requirement
- Proper ADDENDUM process is the ONLY acceptable path for changes

## Status Transitions

Completed specifications can only transition to:
- **Archived**: For long-term storage
- **Reference**: For use as template or example
- **Extended**: Via ADDENDUM system for additional work

No direct modifications to completed specifications are allowed.
